# Concept-Making（戦略的コンセプト策定）

プロジェクト開始時、Overview より先に実行する。ビジネス戦略フレームワークに基づき、
構造的に勝てるポジションを特定してからコンセプトを導出する。

All user interaction in Japanese.
All DB writes via `hub.py` — never raw sqlite3.

```bash
# $HUB is shorthand used in this document.
# Shell state does NOT persist between Bash tool calls.
# Always expand to the full path in each call:
python3 .blueprint-flow/blueprint/hub.py <command> [args]
```

## 決定フロー

<flow name="concept-making">
  <step order="1">ビジネスアイデアのヒアリング: AskUserQuestion で「何を作りたいか」「誰の課題を解くか」を聞く</step>
  <step order="2">競争構造の分析: WTA の4つの力（ネットワーク効果・スイッチングコスト・規模の経済・データフライホイール）が
    どの程度作用する市場かを評価。WTA 崩壊条件（ニーズ異質性・規制分断・技術非連続・信頼分散）から隙間を特定</step>
  <step order="3">戦略軸の選択: 5つのDo戦略からプロジェクトに最適な軸を AskUserQuestion で対話的に決定</step>
  <step order="4">アンチパターンチェック: 選択した方向が5つのDon'tに該当しないか検証。該当する場合はピボット提案</step>
  <step order="5">意思決定・行動原則の確認: 実行に必要な判断基盤を確認</step>
  <step order="6">戦略分析の保存: ... | $HUB set-strategy "市場構造タイプ" "選択した戦略軸" "堀の構造"</step>
  <step order="7">コンセプトの導出・保存: $HUB set-concept "target" "problem" "solution" "value" "catchphrase"</step>
</flow>

## 戦略フレームワーク

### WTA（Winner-Takes-All）の4つの力

| 力 | メカニズム |
|---|---|
| ネットワーク効果 | ユーザー増加が価値を非線形に高める |
| スイッチングコスト | データ・習慣・連携によるロックイン |
| 規模の経済 | ユーザー数増加に伴う平均コスト低下 |
| データフライホイール | 利用データ→モデル改善→ユーザー増の循環 |

### WTA の崩壊条件（隙間の所在）

1. ユーザーニーズの異質性 — 汎用80点では不十分な領域
2. 規制・地政学による市場分断
3. 技術パラダイムの非連続的変化
4. 高リスク領域における信頼の分散

### Do — 5つの戦略軸

| # | 軸 | 要旨 | 問い |
|---|---|---|---|
| ① | 領域特化 | 業界固有データ・規制対応で汎用AIの80点を超える95点を提供 | 汎用では不十分な業界固有課題があるか？ |
| ② | 顧客接点特化 | 既存SaaS統合・コミュニティ浸透・エッジ組込みで届け方で勝つ | 「届け方」で差別化できるか？ |
| ③ | ビジネスモデル特化 | 成果報酬型・OSS+サービス等、巨人が採用しにくい課金構造 | 巨人が真似しにくい収益モデルを作れるか？ |
| ④ | 技術レイヤー特化 | 推論最適化・MLOps・オーケストレーション等、上下のレイヤーを取る | プラットフォームの上下で独自レイヤーを構築できるか？ |
| ⑤ | 規制・地域特化 | データ主権・言語文化・公共セクターで巨人が入りにくい市場を築く | 規制や文化の壁で守られた市場があるか？ |

### Don't — 5つのアンチパターン

| # | パターン | 要旨 | チェック |
|---|---|---|---|
| ① | 汎用性能での正面衝突 | 巨人の最大の強みにぶつかる行為 | 資本・データ・人材の規模勝負になっていないか？ |
| ② | 差別化なきAPI薄ラッパー | 独自データもワークフロー統合もないサービスに堀はない | 「みんなやっている」ことに依存していないか？ |
| ③ | 単一PFへの全依存 | 価格改定・規約変更で事業が破壊される | 他人に判断を委ねる構造になっていないか？ |
| ④ | 検証なき多軸展開 | 単一軸の仮説検証なしにリソース分散 | 小さく張って検証してから集中しているか？ |
| ⑤ | 規制障壁の過信 | 規制だけを堀とし、プロダクト実力で選ばれない | 政策変更一つで崩壊しないか？ |

### 意思決定・行動原則

| Do | Don't |
|---|---|
| 自分の頭で考え、エビデンスで判断する | 権威・多数派に判断を委ねる |
| 反論を想定してから意思決定する | 反対意見を検討しない |
| 掛け合わせで不可替なポジションを築く | スキル単体の積み上げに依存する |
| 教養で判断力の基盤を作り、実践で磨く | インプットだけで満足する |
| 目的を共有する戦略的チームを組む | 仲間意識で馴れ合う |
| 失敗を素早く消し、成功に大きく張る | サンクコストに囚われる |

### 実行原則

```
自社アセットの棚卸し → 最適な単一軸を選択 → MVP/PoCで仮説検証
  → 成功: 2〜3軸に多軸化（攻略コストを指数的に引上げ）
  → 失敗: 損切り・次の軸へ（サンクコストに囚われない）
```

## 保存コマンド

### 戦略分析の保存

```bash
cat << 'EOF' | $HUB set-strategy "市場構造タイプ" "選択した戦略軸" "堀の構造"
（詳細な戦略分析のMarkdown — WTA評価、隙間分析、Do/Don'tチェック結果を含む）
EOF
```

- `$HUB read-core strategy` で確認可能
- 設計変更時は戦略との整合性を必ず確認

### コンセプトの保存

戦略分析の結果から導出する5項目。設計判断・スコープ判断の基準として参照する。

```bash
$HUB set-concept \
  "ターゲット（誰のための製品か）" \
  "課題（ターゲットが抱える具体的問題）" \
  "ソリューション（課題をどう解決するか）" \
  "独自価値（競合にない強み — 戦略軸から導出）" \
  "キャッチフレーズ（20字以内）"
```

- 各項目は1行で、定量的・具体的に記述
- 独自価値は戦略分析の「堀の構造」と整合すること
- ハイレベルコンセプト（キャッチフレーズ）は他4項目が確定してから決定
- `$HUB read-core concept` で確認可能
- 設計変更時はコンセプトとの整合性を必ず確認

## 完了後

コンセプト確定後、`/bpf` に戻って Definition フェーズ（デザイン方向性 → overview → config → tech）に進む。
